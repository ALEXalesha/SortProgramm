# Правила из окна: категории, слова и правило для файла

Дата: 2026-09-23

## Зачем

Правила раскладки сейчас правятся только руками: категории и слова в
`rules.json`, правила для отдельных файлов в `overrides.json`. Для автора это
нормально, для любого другого человека это значит «открой JSON в Блокноте и
не ошибись с кавычкой». README честно рассказывает, сколько бед приходило ровно
этой дорогой: BOM от Блокнота, UTF-16 от PowerShell, категория без строки в
`managed_folders`, хвостовой пробел в имени папки.

Нужно, чтобы человек мог из окна:

- добавить, переименовать и удалить категорию;
- добавить и убрать ключевое слово категории;
- сказать про конкретный файл из плана «всегда класть в эту категорию» и снять
  это правило.

Шаблоны-регулярки (`patterns`) из окна не правятся: обычному человеку
регулярка ничего не говорит. Они остаются в `rules.json` для тех, кто знает.

## Где живут правки

**Отдельный файл `my_rules.json` рядом с `config.json`.** В нём только то, что
человек поменял, и он накладывается поверх `rules.json` при каждой загрузке.

Писать прямо в `rules.json` нельзя: установщик кладёт его заново при каждом
обновлении (`ignoreversion`) — так до уже установленных копий доезжают новые
категории. Правка из окна прожила бы до первой переустановки. Перевести
`rules.json` на «не перезаписывать» — значит вернуть беду, которую когда-то
убрали разделением `config.json` и `rules.json`: новые категории перестанут
доходить до людей совсем.

`overrides.json` остаётся только для чтения, как сейчас. Причина, по которой
его закрыли на запись, прежняя.

Файл хранит отличия, а не копию. Полная копия категорий после первой же правки
молча отрезала бы все будущие обновления правил; копия только тронутых
категорий замораживала бы их по отдельности, и такое поведение никому не
объяснить.

### Формат

```json
{
  "version": 1,
  "categories": {
    "Учёба": {"add": ["курсовая"], "remove": ["haunted"]},
    "Рецепты": {"add": ["рецепт", "recipe"]}
  },
  "renamed": {"Нейросети": "ИИ"},
  "removed": ["Игры"],
  "keep_folders": ["Нейросети", "Игры"],
  "files": {"отчёт.pdf": "Документы"}
}
```

- `categories` — правки слов по категориям, ключ — **нынешнее** имя (после
  переименования). Категория, которой нет среди правил программы, считается
  созданной человеком; созданные встают в конец списка в порядке записи.
  Порядок категорий — это приоритет (`find_category`: первая подошедшая
  выигрывает), так что новая категория слабее всех старых. Это честно:
  человек видит, куда уйдёт файл, прямо в плане.
- `renamed` — имя из `rules.json` → нынешнее имя. Цепочка `A → B → C` хранится
  одной записью `A → C`; переименование обратно в исходное имя запись убирает.
- `removed` — имена из `rules.json`, которые человек удалил.
- `keep_folders` — имена папок, которые остаются «своими», хотя категории с
  таким именем больше нет (старое имя при переименовании, удалённая категория).
  Касается и категорий, созданных человеком: в их папках к этому времени
  могут лежать разложенные файлы.
- `files` — имя файла → категория.

## Как правки накладываются

Порядок: переименования, удаления, правки слов, созданные категории, правила
для файлов. Чистая функция без ввода-вывода: `rules.json` + `overrides.json` +
`my_rules.json` на входе, итоговые правила и уведомления на выходе.

Правила, которые держит само наложение:

1. **Каждая категория — своя папка.** Созданная категория и новое имя сами
   попадают в `managed_folders`. Иначе вышла бы чёрная дыра, о которой уже
   предупреждает `_check_managed`: файлы в папку ложатся, а «Переразложить
   старое» туда больше не заходит.
2. **Старое имя тоже остаётся своим** (`keep_folders`). Иначе после
   переименования папка `Нейросети` с разложенными файлами стала бы чужой, и
   ни переразложить их в `ИИ`, ни убрать пустую папку программа бы не смогла.
   Итог: `managed_folders` только растёт.
3. **Ссылки идут за категорией.** Переименование переносит на новое имя
   шаблоны (`patterns`) и значения `overrides.json`. Удаление снимает шаблоны
   и ручные правила, указывающие на категорию, и называет их в уведомлении.
4. **Слово, добавленное человеком, принадлежит его категории.** Если такое же
   слово есть в другой категории (например, его позже привезло обновление), из
   той оно убирается. Иначе выиграла бы та, что стоит выше, и правка молча
   перестала бы работать.
5. **Правка для категории, которой в правилах больше нет** (обновление её
   убрало или переименовало), не теряется: добавленные слова создают
   категорию с этим именем. Убранные слова для неё просто не нужны.
6. **Созданная категория, совпавшая с новой категорией программы** (регистр
   не важен, как и у Windows), сливается с ней: слова человека добавляются к
   словам программы.
7. **Правило для файла сильнее всего**: выше `overrides.json`, шаблонов и
   слов. Запись `overrides.json` для того же имени (с точностью до
   `name_key`) при наложении убирается, чтобы не спорить. Правило для файла,
   чья категория исчезла, пропускается с уведомлением.

Уведомления идут в `notices`, а не в `problems`: файл прочитан, раскладка
верна, сказать надо (`util.settings_message`).

## Операции

Модуль `sorter/user_rules.py`, без интерфейса. Каждая операция принимает
текущие правки и правила программы и либо возвращает новые правки, либо
бросает `ValueError` с фразой, которую можно показать человеку как есть.
Отказ не меняет ничего.

| Операция | Отказ, если |
| --- | --- |
| `add_category(name)` | имя не годится папкой (`folder_name_problem`), пустое, совпадает с запасной категорией или с существующей категорией без учёта регистра |
| `rename_category(old, new)` | `old` нет; `new` не годится по тем же причинам |
| `remove_category(name)` | такой категории нет |
| `add_word(category, word)` | категории нет; слово после обрезки пробелов короче 2 знаков; такое слово уже есть в этой категории; оно есть в другой категории (ответ называет её) |
| `remove_word(category, word)` | в категории нет такого слова |
| `set_file(name, category)` | категории нет; категория — запасная (это «не знаю», его выбрасывает `_drop_frozen_rules`) |
| `clear_file(name)` | правила для этого файла нет |

Пробелы внутри слова не трогаются: `" фон "` — это существующий приём,
способ потребовать границы слова. Регистр слова сравнивается без учёта, как
в `find_category`.

## Чтение и запись файла

- Нет файла — правок нет, это обычное состояние.
- Файл читается тем же декодером, что и остальные настройки (`util.read_text`:
  UTF-8 с BOM и без, UTF-16, cp1251).
- Испорченный файл или раздел не того типа не роняет запуск: жалоба в
  `problems`, работа идёт с правилами программы, а окно **не записывает** на
  место нечитаемого файла — ровно как с `config.json` (`settings_unreadable`).
  Иначе первое же сохранение заменило бы все правки человека пустыми.
  Отдельные негодные записи внутри читаемого файла пропускаются по одной с
  жалобой.
- Запись атомарная: временный файл рядом и `os.replace`. Оборванная запись
  не оставляет полфайла.
- Установщик `my_rules.json` не поставляет и не трогает. В репозитории файл
  в `.gitignore`: это правки конкретного человека.

## Окно

**Кнопка «⚙ Правила» в шапке** открывает диалог:

- слева список категорий, кнопки «Добавить», «Переименовать», «Удалить»;
- справа слова выбранной категории, поле для нового слова и кнопка «Убрать»;
- правки человека помечены, чтобы было видно, что пришло с программой, а что
  добавлено руками;
- **при вводе слова окно показывает, сколько файлов текущего плана оно
  заберёт и из каких категорий.** Это главная защита от слишком жадного слова:
  `ма` в «Маме» заберёт и «математику», и «макет», и видно это до сохранения;
- диалог работает на копии правок. «Сохранить» пишет `my_rules.json` и
  перестраивает план, «Отмена» не пишет ничего;
- отказ операции показывается под полем ввода той фразой, которую вернул
  `ValueError`.

**Правый клик по строке плана:** «Всегда класть в ▸ категория…» и, если у файла
уже есть правило из окна, «Убрать моё правило». Сразу пишет файл и
перестраивает план — тут нечего подтверждать, результат виден в той же
строке.

**Tk-окно** (запасное, открывается только по `--tk`) редактора не получает. В
README об этом сказано.

## Проверки

**Юнит-тесты** на каждую операцию и на каждый отказ из таблицы, на каждое
правило наложения, на чтение испорченного файла, на атомарность записи.

**Свойства на hypothesis** (`tests/test_user_rules_props.py`), сотни примеров
на каждое:

- после любой случайной последовательности операций (удачных и отказавших)
  итоговые правила согласованы: нет ссылок на несуществующие категории, каждая
  категория есть в `managed_folders`, нет двух категорий с одним именем без
  учёта регистра, `Config.load` не находит новых `problems`;
- `managed_folders` не уменьшается ни от одной операции;
- обратимость: добавить и убрать слово, переименовать и переименовать
  обратно — итоговые категории совпадают с исходными (кроме выросшего
  `managed_folders`);
- отказавшая операция не меняет ни правки, ни файл на диске;
- запись и чтение `my_rules.json` ничего не меняют; любой мусор вместо файла
  (случайные байты, JSON не того вида) не роняет загрузку;
- наложение на «обновлённый» `rules.json` (случайно добавленные и удалённые
  категории и слова) сохраняет правки человека и привозит новое;
- после `set_file(X, C)` классификатор отвечает `(C, «правило»)`, что бы ни
  говорили слова и шаблоны;
- после `add_word(C, w)` файл с `w` в имени уходит в `C`, если его не
  перехватило правило для файла или шаблон.

**Тесты окна**: диалог добавляет и убирает, «Отмена» не пишет файл, счётчик
«заберёт N файлов» совпадает с перестроенным планом, пункты контекстного меню
делают то, что написано.

**Живая проверка**: пересобранный exe, правка правил в окне, план меняется,
перезапуск — правки на месте.
